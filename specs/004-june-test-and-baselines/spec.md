# Feature Specification: An untouched June test, run in the cloud with no laptop

**Feature Branch**: `004-june-test-and-baselines`

**Created**: 2026-11-04. Revised three times the same day, after three reviews of #85 and the owner's decisions. Revised again on 5 November, after the fourth review and the owner's decisions of that day.

**Status**: Draft for the owner. Nothing paid runs and no cloud resource is created before the owner approves.

**Input**: The owner's requests of 4 November 2026 (BUILD_LOG.md, 4 November). This spec delivers one full cloud run with no laptop. The owner uploads the test month's file to the Databricks volume. Its arrival starts a Databricks job. A webhook starts an approval workflow. After the owner approves the figures, a second Databricks job labels and scores, inside Databricks. It writes the results to a volume that holds nothing else. Claude copies them into the repo through a draft pull request. The test month is June 2026, never used before. It answers the question `docs/VALIDATION.md` left open: does the 0.9 hybrid rule beat the LLM alone on untouched data? XGBoost and the fine-tuned transformer are not in this spec (owner decisions). XGBoost moves to a later spec 005.

Requirement IDs are `J1`, `J2` and so on. Tests are named `test_J<number>_...`.

## Rules for every piece

- **J1. June is scored once, after everything is frozen.**
  - Every setting, the hybrid rule, the June sample, the scoring code and the claims are committed before any June label is scored.
  - Then one entry is added to `runs/JUNE_RUNS.md`, which only grows, in its own pull request after the last code change. It names the June list's hash and a hash of the frozen code and configuration, computed by a committed script over `src/`, `config/`, `dbt/`, `splits/`, `pyproject.toml`, `uv.lock`, the job definitions (in `cloud/`), the approval workflow (`.github/workflows/june_approval.yml`), the script itself (`scripts/june_hash.py`) and the July development labels that J7's check reads (`results/eval/v1_dev.csv`, review of #89). Where git is present, the script refuses when the files on disk differ from the tracked ones. The claims of J7 and their numbers are in `config/june_claims.toml`, so they are frozen with the code. Job B runs the code of the commit that merged that entry.
  - **Two gates come first** (owner decision, 6 November). The real entry is written only after both gates pass on the code and the June pin it names: `june-check`, the owner's check of the June zip on the laptop, and `failcheck`, the failing-row check read as the robot in Databricks (J8, `cloud/failcheck/STEPS.md`). Each result, a pass or a fail, is a row of `runs/JUNE_GATES.md`, which only grows and is not frozen, naming its date, the gate, the result, the June pin's SHA-256, the code hash and its evidence. Both June logs' dates are in UTC, as both gates print them. A gate is open for a code and pin when its latest result for them is a pass, so a fail after a pass closes it. Only results dated strictly before the entry count. `scripts/june_hash.py` refuses to print the real entry's hashes unless both gates are open for the current code and pin, with no way round it, and it compares the frozen files with git by content. A test refuses a real entry without both gates open before it, and Job A refuses such an entry too. CI refuses a new real entry whose passes are not already on `main`, so a pass cannot be added with the entry and given an earlier date. A code change after a gate means both gates run again.
  - Job B refuses to score unless the entry's two hashes match what it is about to run.
  - Before its first model call, Job B writes a start marker for that entry in the volume, with a create that fails if the marker exists. It refuses if a marker exists, unless a later entry in `runs/JUNE_RUNS.md` names it as a reproduction, a resume or a second run, with the reason.
  - The dry run (pull request 9) uses a synthetic sample, with its own list hash and its own entry marked synthetic. The real June list matches no synthetic entry. Its list is `splits/june_dry/june_dry.csv`, with its manifest, `SYN-` IDs only, made with its pin `config/june_dry_run.toml` and its mock answers by `scripts/make_dry_run.py` from the synthetic CSV of its round, and Job A and Job B take a synthetic row only with that list (pull request 9a).
  - The laptop path refuses to label or score June at all. `voc label` and `voc evaluate` keep working for July.
  - A later run is logged with its reason, and is a reproduction (the same recorded answers replayed) or a second run, never a quiet rescoring. A run stopped by the spend limit or the quota is not scored. It resumes by replay, under a later entry of the kind "resume", and any new spend needs a new approval of the printed figures.
  - **A run that stops early** (owner decision, 5 November). Scoring refuses unless every complaint of the June list has a result, Product by Product, 2,073 in all. So a run stopped by the spend limit, the quota or a crash gets no verdict, and no result of it has been looked at. Resuming it is therefore not a second look at June. Two rules keep it so:
    - A stopped run writes no per-complaint results file and no figure. It prints only counts and its stop reason. With per-complaint labels and the public June file, anyone could compute partial scores.
    - The resumed run replays every recorded answer already in the volume and calls the model only for the complaints with none, so it pays only for those, and no answer is ever drawn twice to keep the better one.
    - Scoring happens once, only after all 2,073 have a result.
- **J2. The July test set stays sealed.** No June step selects, labels or scores a July test row. Job B's refit loads the whole July export into a temporary DuckDB file, as the laptop does, and selects only the training and development rows (J11, owner decision of 10 November).
- **J3. The same rules as before.** No complaint text in git (B19, B21). Every live call is capped, recorded and approved first (V9). Results that do not favour the LLM are reported the same way. Agreement with the consumer's choice is called that, never accuracy.
- **J4. Complaint text stays in Databricks.** June and July training text, the recordings, the ledger and the fitted TF-IDF + LR model stay in the volume. The text leaves Databricks only to the Anthropic API, in tool-less calls. GitHub receives only numbers (the estimate). The results files (J11) reach the repo only through Claude's copy and a draft pull request. No runner, artifact, cache, log or model hub ever holds complaint text.
- **J5. What a job may print.** The repo is public, so its Actions logs are public. Every job and workflow prints only IDs, labels, reasons, positions, decisions and counts, through B21's shared error handler, with no traceback, no debug or verbose logging and the SDK's debug logging off. A test runs each entry point on hostile synthetic text and checks the output. Job A is a notebook task that ends with `dbutils.notebook.exit` and a JSON of fixed keys (counts and the worst case). A workflow reads only those keys from the run's output, and never prints `error`, `error_trace`, `logs`, `state_message` or a termination message.

## The pieces

- **J6. The June sample.**
  - `voc sample june`, on the laptop, as for July. It reads the pinned June CSV, the one inside the zip, and pins it in `config/data_files.toml`, with its folder in the variable `VOC_JUNE_DATA_DIR`.
  - Copies within June are removed, and so is any June complaint whose narrative copies one in July's training or development sets (owner decision, the July test set stays sealed). July's copies go first, because July's rows are the earlier ones, so a June row is never lost through a June near-copy that was itself a copy of July (review of #88).
  - Every June Product must be in `config/labels.toml` (B24), or the sample refuses.
  - Its size by Cochran's formula (B25) at e = 2 points, with N the June pool after copies are removed: about 2,080 if about 1,270 copies go, and 2,102 if none do. The exact n comes from the June count. Split across Products in proportion. Drawn by the owner on 5 November (`voc sample june`): 1,701 copies removed (938 of July, 646 exact and 117 near within June), a pool of 15,119 and n = 2,073.
  - Frozen with its hashes in `splits/june/`. The read guard protects `VOC_JUNE_DATA_DIR`, and the merge check drops it, as for July and August.
- **J7. The June scoring and its claims.**
  - On the June sample, the LLM (claude-haiku-5-5, prompt v1, unchanged) labels every complaint once. TF-IDF + LR is refit from July's training rows only, with its settings unchanged. The refit model must reproduce the committed July development labels in `results/eval/v1_dev.csv` before it labels June.
  - The hybrid is the rule fixed on 2 November, unchanged: TF-IDF + LR answers at a top confidence of 0.9 or more, else the LLM. A held-back LLM label counts as wrong.
  - Scores are re-weighted by June's own pool after copies are removed, so they are not directly comparable with July's, whose product mix differs. Intervals come from a paired bootstrap of 2,000 draws within each Product, seed 0.
  - **The one primary claim, fixed now:** the hybrid against the LLM alone, both at full coverage, as V6 scores it. The hybrid beats the LLM if the 95% interval of the point difference is wholly above zero. It does not beat it if the point difference is zero or below. Otherwise it is inconclusive. When both tests apply, "does not beat" wins: a win needs both a point difference above zero and a 95% interval wholly above zero (owner decision, 5 November, review of #89). The claims and their numbers are in `config/june_claims.toml`.
  - **One secondary comparison, with its interval and no verdict:** the LLM against TF-IDF + LR at the same coverage, as B10 defines it.
  - **Cost per extra correct label:** against TF-IDF + LR at the same coverage, as V6's headline, with the full-coverage view next to it.
- **J8. The full cloud run.**
  1. Last of all the owner's steps, the owner uploads the June zip to `voc_raw/incoming/`.
  2. **Job A** starts on its arrival (file-arrival trigger on that folder, which cannot filter by extension, so `unpack` refuses anything but one zip holding one CSV). It unzips the file into `voc_raw/june/`, outside the trigger folder, checks the CSV against its pin, runs the same dbt models as the July build (with June's own row count in the data tests), counts the rows and the narratives Spark reads from the file with dbt's own read options and refuses unless they are the pin's, from the owner's check on the laptop (owner decision, 6 November), selects the frozen sample's IDs and checks their hashes against `splits/june/`. Until pull request 6b lets it read the June ledger's use, it refuses a later row of `runs/JUNE_RUNS.md` (a resume, a reproduction or a second run), whose figures would otherwise be a full run's (owner decision, 6 November). It computes the numbers for the approval: the call count, the expected cost, the worst-case tokens and the tokens left under the cap. It makes no model call and prints counts only.
  3. Job A's success webhook goes to the receiver (J9). The receiver starts the approval workflow (J10) with Job A's run ID.
  4. The approval workflow reads Job A's numbers from its run output and prints them. Its second job waits for the owner's approval in the `june-run` environment, then starts **Job B** with `run-now`, passing Job A's run ID and its own GitHub run ID.
  5. **Job B** (J11) labels and scores inside Databricks and writes the results files to the results volume `voc_results`.
  6. The approval workflow follows Job B through the jobs API until it ends, then posts a signed result message to the receiver.
  7. Claude copies the results files from `voc_results` with the reader's credential (J13), on a branch `results/june-<run ID>`, and opens a draft pull request, as usual (owner decisions). CI's checks (the secret scan, the names check, the size limit and the CFPB header check) run on the copied files before anything reaches `main`.
  - **The webhook fallback:** the destination's form had no test button on 9 November, so the dry run's Job A run is that test. If it shows that Databricks' webhooks cannot reach the receiver, the owner starts the approval workflow by hand once Job A has succeeded, with Job A's run ID read from the job's page in Databricks. Every run of the workflow has a Job A run ID, so its name ties the approval to that run (J16). Job B is followed the same way in both cases.
- **J9. The receiver.** A small Azure Function, apart from the public app, which stays read-only.
  - Two functions: an HTTP function that takes the calls, and a queue function that does the work. The maximum instance count is 1, the lowest allowed, which applies to each of the two, so at most 2 instances run. Instance size 512 MB, with no always-ready instance. Each instance takes 4 HTTP calls at once, set by hand in the portal (`receiver/plan.json`). Python apps take one by default. With one, in the live test of 7 November, the second of two calls in a row got no answer within 40 seconds. The live check sends its signed message straight after its badly signed one, so the signed message was lost every time. With 4, three calls in a row were all answered, the slowest in 2.0 seconds.
  - The HTTP function checks the caller before it replies. Databricks' webhook carries HTTP Basic sign-in, compared in constant time. The approval workflow's result message carries an HMAC-SHA256 over the timestamp, a dot and the raw body, with a shared secret, compared in constant time, and refused if the timestamp is more than 5 minutes old or more than 1 minute ahead. A refused call gets 401 and is not queued.
  - An accepted call gets 202 at once and goes on the queue.
  - Duplicates: each event's key (Databricks: the job run ID and event type, the result message: the GitHub run ID and run attempt) is written to a table with an insert that fails if the key exists. A repeat is acknowledged and dropped. Keys are kept for 30 days.
  - The queue function asks Databricks itself whether that run really succeeded, for the June job, with the robot account's credential (J13), which can view Job A's and Job B's runs, and start or cancel Job B. Then it starts the approval workflow. Before it does, it checks GitHub for a run of that workflow whose `display_title` is exactly the name J16 gives for that Job A run ID, so a retried dispatch cannot start a second one.
  - The signed result message is stored in the table with its status and counts, and logged with IDs and counts only. It starts nothing.
  - Failures: the queue retries by its visibility timeout, at most 5 tries in all, then moves the message to the failure queue, logged with IDs and counts only.
  - Its secrets are in an Azure Key Vault, read by the Function's managed identity. Its app settings hold only Key Vault references. No secret is in code, a log or the repo. It logs IDs, event types, statuses and counts only. Application Insights is off, except for a diagnosis, then removed (`docs/RECEIVER_STEPS.md`).
  - Tests for each: a bad sign-in, a bad signature, an old or future timestamp, a duplicate, the 202 reply before the work, a dispatch already made, and a retry that ends in the failure queue.
  - **The code, in `receiver/`** (pull request 7). `receiver_core.py` holds the logic, with no Azure, Databricks or GitHub library, so the tests run it with fakes. `receiver_adapters.py` links it to the table and the queue (by the Function's managed identity), to Databricks (the robot's OAuth credential) and to GitHub (the "Actions" token). `function_app.py` holds the two HTTP routes, `databricks` and `result`, and the queue function. `host.json` sets 5 tries, after which the Functions runtime moves the message to its failure queue, `june-events-poison`. `plan.json` holds the plan's settings for the owner to set in the portal, and `app_settings.json` the app settings, every secret as a Key Vault reference. `requirements.txt` pins the packages for Python 3.12. The queue function deletes event keys older than 30 days before its work, and a failed purge is logged and never blocks the work. The settings refuse an empty secret, or a Key Vault reference Azure left unresolved, since that text is public in this repo. A body over 16 KB gets 413 before any check. The service clients are made once, on first use. The adapters run against the real services first in the dry run of pull request 9.
  - **The deploy** (owner decisions, 6 and 7 November). `.github/workflows/deploy_receiver.yml`, started by the owner by hand on `main`, never by Claude.
    - It runs in the GitHub environment `receiver-deploy`, limited to `main`, and signs in to Azure with OpenID Connect as its own identity, `voc-receiver-deploy` (J13). That identity trusts only this environment's token, so the dashboard's deploy, which has another identity and no environment, cannot reach the receiver.
    - It stops when `main` has moved on since its commit, so a re-run of an old run never rolls the receiver back, and it fails when any of its secrets is unset.
    - It packs only the receiver's own files, `function_app.py`, `host.json`, `requirements.txt` and the two modules, plus `BUILD_COMMIT`, the commit. It deploys them with `az functionapp deployment source config-zip --build-remote true`, which the Flex Consumption plan builds from `requirements.txt` ("Deployment technologies in Azure Functions" and "Python build options", read on 7 November). The CLI's own output and error text are kept out of the public log, which shows its exit code only. The details of a failure are in the Azure portal.
    - Every reply of the receiver's own code names its commit in `X-Voc-Build`. An unhandled error, which the platform answers, has no such header. The deploy then checks that an empty POST to the result route gets 401 from this commit, so an old instance that still answers does not count. On a failure it prints the last try's status and one fixed word: this commit, another commit or no header. A failed upload prints its exit code and one fixed word from the CLI's error text, never the text: authorization, not found or other.
    - The app's name, its resource group and its address are secrets of the `receiver-deploy` environment, so they reach only this workflow's job on `main`, and the receiver's address is not in this public repo. The deploy's check needs the receiver's own settings to load, so `VOC_BASIC_USER`, `VOC_BASIC_PASSWORD`, `VOC_HMAC_SECRET` and `VOC_JOB_A_JOB_ID` hold a value before the first deploy (`docs/RECEIVER_STEPS.md`). The deploying identity needs the Website Contributor role on the Function app ("Continuous delivery by using GitHub Actions", read on 7 November).
  - **Lazy clients** (owner decision, 6 November). The queue function makes its Databricks and GitHub clients only when a message needs them. A result message needs neither, so it is stored with no Databricks or GitHub setting at all.
  - **The live check** (owner decisions, 6 and 7 November). Once the receiver is deployed, the owner runs `scripts/receiver_live_check.py` with the receiver's address. It asks for the HMAC secret with a hidden prompt, never as an argument, since PowerShell keeps command lines in its history file. It sends one synthetic result message signed with a wrong key, which must get 401, and one signed with the secret, which must be queued, 202. It prints the two status codes, a verdict and the message's key only. The message names GitHub run 1, Job A run 1, Job B never started, and as its attempt the Unix time of the check, so each run has a fresh key and is never taken as a duplicate. A 202 means queued. The proof that the receiver stored it is the `result` row with that key in its table, which the owner checks and then deletes with its `event` row (`docs/RECEIVER_STEPS.md`). It needs no Databricks setting and no GitHub token, and starts nothing.
  - **Its identity.** The Function's system-assigned managed identity reads the Key Vault (Key Vault Secrets User). It uses the queue with Storage Queue Data Contributor, which covers reading and deleting messages, and the table with Storage Table Data Contributor. Its own storage, for its host and its code package, uses this identity too, with Storage Blob Data Owner on the account and Storage Blob Data Contributor on the package's container, both given by the portal. It is never the storage account's key. The deploy identity can read the app's settings through Website Contributor, so a key there would give it the storage. These roles were checked in the portal on 7 November.
- **J10. The approval workflow.**
  - Started only by `workflow_dispatch` on `main`, from the receiver or by the owner. Claude never starts it.
  - Its one input is Job A's run ID, `job_a_run_id`, required in every run, the fallback's included, checked as a whole number and passed to commands through `env:`, never written into a `run:` script. Its `run-name` holds that ID (J16).
  - First job, in the environment `june-figures` (main only, no reviewer): it holds the robot account's credential, reads Job A's numbers and prints them.
  - Second job, in the protected environment `june-run` (main only, the owner as required reviewer, "prevent self-review" off so the owner can approve a run the owner's dispatch started): it holds the robot account's credential and the HMAC secret, starts Job B, follows it, and posts the signed result message.
  - Permissions per job, read-only repo access, one run at a time (a `concurrency` group), and every action pinned by its commit SHA.
  - **Built in pull request 8.** The workflow is `.github/workflows/june_approval.yml`. Its logic is `src/voc/approval.py`, run with the runner's own Python (`python3 -I`) and its standard library only, so it is frozen with the code (J1) and installs nothing. Each job reads its own run first (J16 item 3), and both jobs check Job A's run in full (item 5), the second again after the approval. The second job refuses any run attempt but the first before it starts Job B, and posts `NOT_STARTED` when it refuses. It follows Job B one look a minute until 330 minutes after the job's start, which leaves 30 of the job's 360 minutes for Job B's exit value and the result post, and then posts `UNKNOWN`. A failed or broken look is tried again at the next one.
